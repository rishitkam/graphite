Exhibit A

Two reads, on purpose

The brief got read twice, independently — once as a judge deciding what actually earns points, once as an engineer looking for where the thing breaks. Pass two was written without re-opening pass one's notes, so agreement between them is a real signal, not an echo. Both full passes and the line-by-line comparison are saved as their own files alongside this page.

Pass 1 — read it like a judge

what is this rubric actually rewarding?
  • No isFraud column anywhere — this is graded like a case-file audit, not a leaderboard.
  • "Not every pattern is documented" — the five typologies are a floor, not the whole test.
  • The answer file wants the recommendation twice: before new evidence, and after. A one-shot pipeline structurally can't produce that.
  • TigerGraph MCP is a required, separately-graded component — not incidental plumbing.
  • Actions may be stubbed — judges are scoring the decision layer, not a Twilio integration.

Pass 2 — break it like an engineer

where does this actually fail in the real world?
  • Any threshold tuned by eyeballing the 20 benchmark cases is overfit to a hand-picked sample.
  • "Similar case was cleared" can just be a human's old mistake, laundered as data.
  • A fully transparent, deterministic policy is exactly what an adaptive fraud ring learns to route around.
  • Heavy graph algorithms computed live, per case, will not survive a real latency budget — or a demo.
  • "Enough evidence to act" is a cost-of-waiting problem, not a confidence percentage.

Where they agreed — highest-confidence signal

  • Action execution needs a hard gate — one pass got there from the grading rules ("only authorized actions may be executed"), the other from safety (a poisoned merchant-name field shouldn't be able to talk an LLM into moving money). Same conclusion, unrelated reasons.
  • Case memory has to justify itself, not just retrieve — one pass flagged it as the innovation opportunity, the other as the bias-laundering risk.
  • The five typologies are a floor — the brief says so outright, and separately, pattern-matching against a fixed list simply doesn't generalize.

Exhibit B

The build: propose everywhere, execute nowhere near the model

The orchestrator — call it the detective — can read anything on the graph and propose anything as a next step. It cannot execute anything. The only way an action actually runs is through a separate, boring, deterministic rulebook that reads structured fields, never model output, and hands out an approval ticket. That single split answers both halves of Exhibit A's first convergence point at once.

Exhibit C

When to stop investigating

A confidence threshold treats every extra fact as free. It isn't: a step-up prompt spends a customer's patience, an analyst request spends their afternoon, and a card that's actively being drained spends real money by the minute it waits. Graphite prices the next fact against the cost of waiting for it, and stops exactly when the answer to "is one more question worth it" turns from yes to no.

Cheap and reversible (a temporary hold, a step-up prompt) → act immediately, keep investigating in parallel. Expensive and irreversible (closing an account, filing a report, denying a legitimate transaction) → the higher confidence bar still applies, no matter how urgent the exposure feels.

Exhibit D

Case memory that's allowed to disagree

Retrieval blends two signals: shared structure with past cases (same device, same email, same ring — cheap, high-precision) and semantic similarity of the case narrative (catches the same trick told in different words). The result has to name which shared entities justify the match — and the orchestrator explicitly checks whether its own read of the evidence agrees or disagrees with what the precedent concluded.

PRECEDENT · CASE #4192 — confirmed fraud AGREES
match: shared device fingerprint + card BIN, 11 days apart

Same device funded two "different" identities before. This case shows the same shape — recommend block + SAR.

PRECEDENT · CASE #3810 — cleared DISAGREES
match: similar merchant category and amount band only

Surface similarity only — no shared device, email, or IP. Treated as new and unrelated, not deferred to.

Exhibit F

Trade-offs made on purpose

Every one of these had a real alternative. Here's what got picked over what, and why.

DecisionChosenOverWhy
OrchestrationLangGraph state machineRole-based multi-agent crewThe brief's flow is a strict sequence with one real loop-back — an explicit state graph matches that shape and makes the two checkpoints easy to pin down.
Action authorizationDeterministic policy engine issues ticketsLLM calls tools with a confirmation promptA confirmation still trusts the model's read of attacker-influenced text. Separating propose from execute removes that failure class entirely.

What we'd revisit with more time

  • Real probabilistic entity resolution instead of deterministic key-matching.
  • Fit the stopping rule's cost estimates against the full closed-case history instead of seeding them by hand.
  • A fairness pass on memory-driven recommendations — the disagreement signal guards against this, it doesn't solve it.
  • Version the policy engine's rules like code, since it's the one component a regulator would actually want to inspect.
